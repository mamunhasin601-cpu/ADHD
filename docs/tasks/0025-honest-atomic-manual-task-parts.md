# Task 0025 - Honest atomic manual task parts

## Status and scope

Completed. An ordinary root task can own an optional, user-authored checklist of
manual parts. The task form owns one local draft and persists the parent and the
authoritative parts array only when Save succeeds. This capability is not AI
decomposition, a routine, recurrence, focus-session state, or automatic planning.

`firstStep` and `subTasks` remain separate concepts. `firstStep` is one optional
entry action for difficult-start support. `subTasks` are checklist parts of the
larger task. Parent completion never completes parts implicitly, and completing
all parts never completes the parent.

## Atomicity and ownership

Supplying `subTasks` on root create or update is authoritative. The write shape is
`{ id?: UUID, title: string, completed?: boolean }`; create rejects client IDs.
Titles are trimmed, non-empty, at most 240 characters, and each draft contains at
most 50 parts. Duplicate, foreign, wrong-parent, nested, recurring, occurrence,
and unauthorized references are rejected. Scheduling, recurrence, reminder,
timestamp, first-step, ownership, and parent fields are not accepted inside a
part write.

Parent create/update and every part insertion, retention, update, and removal run
in one Prisma transaction. Existing IDs stay stable, new IDs are generated by the
server, and omitted existing parts are deleted. Any failure rolls back the parent
and every part change. Reminder synchronization runs only after commit and only
for the root task. A failed mobile save retains the complete local draft for an
identical retry; synchronous submit locking prevents duplicate mutations, and
continuation ownership suppresses stale navigation, errors, and cache effects.

The omitted-`subTasks` path remains backward compatible. Legacy direct part writes
remain available for ordinary root parents, but cannot add time, duration,
recurrence, first-step, nested parts, independent start state, or reminder side
effects.

## Deletion and counting

Deleting a non-recurring parent deletes the parent and all part rows atomically.
The self-relation uses `ON DELETE CASCADE`, so a part cannot be orphaned or
promoted into a root Thought even if deletion is performed outside the service
transaction. Cleanup receives both the root and part identities.

Only root tasks consume the free-tier active-task allowance. Parts are excluded
by `parentTaskId: null`, do not appear as independent Today/Thoughts rows, and
never own reminders. Recurring templates and occurrences continue to reject
manual parts.
