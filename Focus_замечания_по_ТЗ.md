# Focus (СДВГ-планер) — замечания и предложения по ТЗ

Собрано по итогам мозгового штурма поверх исходного ТЗ для Claude Code.

---

## 1. Продуктовые ADHD-фичи и UX

### Снижение фрикции на "входе" (критично для СДВГ)
- Приложение открывается сразу на "сейчас" — таймлайн, отцентрованный на текущем моменте, не список и не меню
- Создание задачи в 1 тап из любого места — плавающая кнопка, не форма с обязательными полями. Время/длительность можно оставлять пустыми и доразмечать позже
- Виджет на главном экране — отметка "готово" одним тапом прямо с экрана блокировки, без открытия приложения

### Работа с параличом выбора и прокрастинацией
- "Разбей на шаги" — готовые шаблоны подзадач для типовых дел (не AI, а простые пресеты: "убраться в комнате" → мусор/пол/поверхности)
- "Задача-затравка" (2-минутное правило) — опциональное поле "с чего начать" для снижения порога входа в задачу

### Мягкость вместо давления
- "Мягкий старт" задачи — зона времени вместо жёсткого дедлайна (например, "утренняя рутина: 8–10"), чтобы не создавать тревогу от пропущенного точного времени
- При невыполненной задаче — не красный крестик/чувство вины, а нейтральное "перенести?" в один тап
- Вариативность тона уведомлений (нейтральный/подбадривающий) — резкий тон плохо работает при rejection sensitivity, характерной для СДВГ
- Стрики — с осторожностью: streak + СДВГ = тревога после первого пропуска и забрасывание всего. Рассмотреть накопительную метрику без обнуления вместо классического streak

### Body doubling
- Рекуррентные фокус-сессии по расписанию (не только спонтанные комнаты) — "каждый будний день в 10:00"
- Явный статус "просто присутствие" (камера выключена) как равноправный режим, не как "недо-участие"
- Модерация публичных комнат с первого дня (жалобы, бан) — обязательна для уязвимой аудитории, репутационный риск иначе

## 2. Технические риски и стек

### Daily.co + Expo — самое рискованное место в плане
- Подключение Daily SDK ломает Expo Go (нужен dev-client / EAS Build) — стоит закладывать это как отдельную веху с самого начала, не как "апгрейд" в процессе Этапа 7–8
- Альтернатива: держать dev-client окружение с начала проекта, чтобы не было регресса при переходе к body doubling

### Надёжность push (уже отмечена в ТЗ как боль конкурентов)
- Idempotency-ключи в BullMQ джобах — чтобы retry не задваивал уведомления
- Версионирование `expo_push_token` и обработка `DeviceNotRegistered` — автообновление токена при каждом запуске
- Тестировать recurrence rules и напоминания на переходе через DST / смену часового пояса пользователем (поездка), не только на статичном TZ

### Прочее
- Использовать `npx expo install`, а не обычный `npm install` для нативных Expo-модулей — иначе риск несовместимых версий
- Turborepo подключать по мере реальной боли с кэшированием сборок, на старте достаточно npm workspaces

## 3. Монетизация и GTM

### Go-to-market через Telegram-сообщества
- Партнёрство с админами каналов (в т.ч. психологами из раздела про КПТ-контент) эффективнее холодной рекламы — уже доверенный источник для аудитории
- Закрытая бета среди подписчиков 1–2 каналов с обратной связью в том же чате — дешёвая быстрая валидация body doubling до вложений в полноценный релиз
- Body doubling — уже существующий паттерн в этих сообществах (ручные созвоны в Zoom) — сильный сигнал product-market fit, стоит явно спросить комьюнити, чем их не устраивает текущий процесс

### Монетизация
- Freemium: таймлайн + рутины бесплатно всегда, body doubling — платно / с лимитом в бесплатном тарифе
- In-app purchase в App Store/RuStore сталкивается с трением (нет иностранных карт у части аудитории) — предусмотреть прямую оплату (ЮKassa/CloudPayments), особенно для веб-версии. Важно свериться с политиками Apple/Google насчёт обхода in-app purchase
- Daily.co тарифицируется по минутам участников — при щедром бесплатном лимите можно упереться в расходы ещё до первой оплаты, стоит зафиксировать unit-экономику заранее

## 4. PWA vs нативное приложение — вопрос уведомлений

Рассматривался вариант чистого веба (Next.js) с установкой ярлыка на экран телефона вместо React Native/Expo.

### Что упрощается при переходе на PWA
- Отпадает вся инфраструктура Expo/React Native, Android Studio, Xcode, `expo prebuild`, dev-client для Daily.co
- Daily.co имеет обычный JS SDK для браузера — WebRTC работает без нативной сборки
- Не нужна публикация в App Store / RuStore
- Один кодбейс вместо трёх приложений

### Риски уведомлений в PWA
- **Android/Chrome** — Web Push работает полноценно, поведение близко к нативному. Риск — агрессивные "оптимизации батареи" у Xiaomi/Samsung/Huawei (управляемо через исключения)
- **iOS/Safari** — работает только с iOS 16.4+; обязательна установка именно через "Добавить на экран «Домой»" (просто вкладка в Safari не работает); разрешение на уведомления запрашивается только после запуска с ярлыка — лишний шаг, часть пользователей его не пройдёт; нет доступа к time-sensitive уведомлениям (привилегия нативных приложений через APNs)
- Ключевой риск: в ТЗ явно указано, что надёжная доставка уведомлений — способ отстроиться от конкурентов. PWA-путь добавляет к этой задаче ещё один слой нестабильности, специфичный для iOS, а не устраняет исходную проблему

### Данные по доле iOS/Android в России (для оценки риска)
- Т-Банк (T-Pay, 2022–2024): Android 58–60%, iPhone 40–42% среди пользователей
- «Ведомости» (2026): среди брендов — Xiaomi 23%, Samsung 19%; iPhone используется примерно каждым четвёртым россиянином (~25%)
- В городах-миллионниках доля iPhone заметно выше среднего — 48% в 2025 году, в Казани и Петербурге iPhone даже лидирует над Android
- Apple занимает 27–28% рынка в деньгах, но всего ~8% в штуках проданных за период устройств (люди дольше не меняют iPhone, поэтому установленная база выше, чем доля в новых продажах)
- Продажи iPhone в РФ в 2026 году падают (–10…–30% в первом полугодии) на фоне общей экономии и высоких ставок по кредитам

**Рабочий ориентир:** 25–40% аудитории на iOS, с поправкой на то, что аудитория Focus (взрослые, готовые платить за нишевое приложение, вероятно из крупных городов) статистически ближе к верхней границе или выше.

**Рекомендация:** не переходить на PWA только ради упрощения разработки, пока нет точных данных по своей аудитории — доля iOS слишком велика, чтобы списывать со счетов. Следующий шаг — прямой опрос в целевых Telegram-каналах.

## 5. Открытые вопросы (обновлённый список)

- Нужна ли веб-версия в MVP или отложить до валидации спроса
- PWA vs нативное приложение — решение зависит от реальной доли iOS/Android в аудитории (см. раздел 4); нужен опрос в Telegram-каналах
- Регистрация в RuStore — начинать заранее, отдельный процесс
- Момент перехода с Daily.co на self-hosted signaling — зафиксировать метрику-триггер (например, >30% активных пользователей регулярно используют body doubling)
- Модель монетизации и способ оплаты (in-app purchase vs прямая оплата ЮKassa/CloudPayments) — требует уточнения политик платформ
- Опрос в Telegram-сообществах стоит сделать комплексным: доля iOS/Android + привычка к PWA-паттерну + готовность платить за подписку — закрыть сразу несколько открытых вопросов одним действием
